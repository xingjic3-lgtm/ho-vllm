# V2｜Packed Serving + Paged KV Cache

## 1. V2 的起点

V1 已经实现了多 Request 调度和 Continuous Batching，但在实际实现中暴露出了几个明显的问题：

1. `[B, T]` 形式的二维 `input_ids` 会产生大量 Padding 计算。
2. 每次生成时，历史 Token 的 K/V 会被重复计算。
3. V1 中 Engine、Scheduler、模型执行和 KV 管理职责混在一起，架构逐渐变得冗杂。
4. 模型末尾会对所有 Hidden State 计算 Logits，但真正需要采样的通常只有少数位置。

V2 围绕这些问题重新设计 Serving 执行链。

---

## 2. 从 Padding Batch 到 Packed Input

V1 使用二维输入：

```text
input_ids: [B, T]
```

Batch 中不同 Request 的长度通常不同，但 Tensor 的第二维 `T` 必须一致，因此短序列需要补 `PAD`：

```text
Request A: [A0 A1 A2 A3 A4]
Request B: [B0 B1 PAD PAD PAD]
Request C: [C0 C1 C2 PAD PAD]
```

这些 PAD 虽然没有实际语义，但仍然会进入模型和 Attention 计算，造成计算浪费。

因此 V2 改为 **Packed Input**：

```text
[A0 A1 A2 A3 A4 B0 B1 C0 C1 C2]
```

此时：

```text
input_ids.shape = [N]
```

其中：

```text
N = 所有 Request 本轮实际计算 Token 数之和
```

不再存在 Padding Token。

### query_start_loc

Packed 之后，不同 Request 的 Token 被拼接到同一个一维 Tensor 中，因此模型需要知道每个 Request 在 Packed Tensor 中的范围。

引入：

```text
query_start_loc
```

例如：

```text
A: 3 tokens
B: 1 token
C: 2 tokens
```

Packed Input：

```text
[A0 A1 A2 B0 C0 C1]
```

对应：

```text
query_start_loc = [0, 3, 4, 6]
```

于是：

```text
A → [0:3]
B → [3:4]
C → [4:6]
```

`query_start_loc` 解决了 Packed Input 中不同 Request 的边界问题。

## 3. 引入 KV Cache

在自回归生成中，如果每一步都重新传入完整序列：

```text
第 1 步：[A B C]
第 2 步：[A B C D]
第 3 步：[A B C D E]
```

那么历史 Token 对应的 K/V 会被反复计算。

但历史 Token 的 K/V 在生成过程中不会改变，因此没有必要重复计算。

于是 V2 引入 **KV Cache**：

```text
历史 Token
    ↓
K / V 计算一次
    ↓
保存到 KV Cache
    ↓
后续直接读取
```

引入 KV Cache 后，模型输入也随之改变。

不再每一步传完整序列，而只传：

```text
当前真正还没有计算过的 Token
```

例如 Decode 阶段：

```text
历史：
[A B C D] → 已存在 KV Cache

当前：
只输入 E

Q(E)
×
K(A B C D E)
```

因此 Scheduler 需要维护：

```text
request.num_computed_tokens
```

并根据：

```text
request.num_tokens - request.num_computed_tokens
```

决定当前 Request 本轮还需要计算多少 Token。

---

## 4. 重新划分架构职责

V1 中请求状态、调度、模型输入构造和 KV 管理逐渐混在一起。

V2 将 Serving 核心重新划分为：

```text
Request
    ↓
Scheduler
    ↓
SchedulerOutput
    ↓
ModelRunner
    ↓
Model / Attention
```

同时：

```text
KVCacheManager
```

负责独立管理物理 KV Block。

### Request

保存单个请求的长期状态：

```text
prompt_token_ids
output_token_ids
all_token_ids
num_computed_tokens
sampling_params
status
```

### Scheduler

负责决定：

```text
本轮哪些 Request 执行
每个 Request 本轮执行多少 Token
```

输出：

```text
SchedulerOutput
```

其中包含：

```text
scheduled_requests
num_scheduled_tokens
```

### KVCacheManager

负责：

```text
Request → Physical KV Blocks
```

也就是管理物理 KV Block 的分配和释放。

它不负责实际计算 K/V。

### ModelRunner

负责把 Scheduler 的 Request 视角转换成模型真正需要的 Tensor 和 Metadata：

```text
input_ids
positions
query_start_loc
seq_lens
block_table
slot_mapping
```

### Attention

负责：

```text
计算 Q/K/V
写入当前 K/V
读取历史 K/V
执行 Attention
```

## 5. Paged KV Cache

KV Cache 不使用每个 Request 一块连续的大 Tensor，而是按固定大小划分成 Block。

例如：

```text
block_size = 16
```

Token Position 与 Logical Block 的关系：

```text
logical_block_id = position // block_size
block_offset     = position % block_size
```

每个 Request 再通过 `block_table` 将 Logical Block 映射到实际 Physical Block。

例如：

```text
block_table:

logical block 0 → physical block 7
logical block 1 → physical block 3
logical block 2 → physical block 9
```

因此 Position 20：

```text
logical_block_id = 20 // 16 = 1
block_offset     = 20 % 16 = 4

physical_block_id = block_table[1] = 3
```

最终位置：

```text
physical block 3
offset 4
```

---

## 6. KV Cache 写入：slot_mapping

当前计算出的 K/V 需要知道应该写入 KV Cache 的哪个位置。

因此 V2 构造：

```text
slot_mapping
```

每个当前计算 Token 对应一个 Slot：

```text
slot = physical_block_id * block_size + block_offset
```

例如：

```text
physical_block_id = 3
block_offset = 4
block_size = 16
```

则：

```text
slot = 3 * 16 + 4 = 52
```

Attention 中再恢复：

```text
physical_block_id = slot_mapping // block_size
block_offset      = slot_mapping % block_size
```

然后写入：

```python
kv_cache[0, physical_block_ids, block_offsets] = K
kv_cache[1, physical_block_ids, block_offsets] = V
```

因此：

```text
slot_mapping
```

负责解决：

> 当前这些 Token 计算出的 K/V 应该写到哪里。

---

## 7. KV Cache 读取：block_table + seq_lens

写入 KV Cache 后，Attention 还需要读取每个 Request 的历史 K/V。

这里主要依赖：

```text
block_table
seq_lens
```

### block_table

表示一个 Request 的：

```text
Logical Block → Physical Block
```

映射。

### seq_lens

表示当前 Request 在本轮计算完成后拥有多少个有效 Token。

例如：

```text
之前已经计算 300 Token
本轮再计算 200 Token
```

则：

```text
seq_len = 500
```

Attention 根据：

```text
block_table
+
seq_len
```

找到这个 Request 当前完整的历史 K/V。

因此：

```text
slot_mapping
```

解决写入问题；

```text
block_table + seq_lens
```

解决读取问题。

## 8. Chunked Prefill 与统一调度

有了：

```text
num_computed_tokens
num_scheduled_tokens
Paged KV Cache
```

之后，一个很长的 Prompt 不需要一次性全部计算。

例如：

```text
Prompt = 1000 tokens
max_num_batched_tokens = 256
```

可以拆成：

```text
256
256
256
232
```

逐轮完成 Prefill。

这就是 Chunked Prefill。

同时 Decode Request 可能每轮只需要：

```text
1 token
```

因此同一轮可以出现：

```text
Request A：Decode 1 token
Request B：Prefill 200 tokens
Request C：Prefill 55 tokens
```

最终全部 Pack 成：

```text
[N]
```

统一进入一次模型 Forward。

这样 Prefill 和 Decode 不再需要两套完全独立的模型执行路径。

## 9. Selective Logits Computation

模型最后通常执行：

```text
hidden_states
    ↓
lm_head
    ↓
logits
```

V1 中所有 Hidden State 都会经过 `lm_head`。

例如：

```text
hidden_states.shape = [256, hidden_size]
```

则会计算：

```text
logits.shape = [256, vocab_size]
```

但对于自回归生成来说，真正需要采样的通常只有 Request 当前最后一个有效 Token。

因此其余 Logits 都属于冗余计算。

V2 引入：

**Selective Logits Computation**

先记录真正需要 Logits 的 Packed Position：

```text
logits_indices
```

然后：

```python
sample_hidden_states = hidden_states[logits_indices]
logits = model.compute_logits(sample_hidden_states)
```

执行链从：

```text
[N, H]
↓
LM Head
↓
[N, V]
```

变为：

```text
[N, H]
↓
选择需要采样的位置
↓
[M, H]
↓
LM Head
↓
[M, V]
```

其中：

```text
M << N
```

特别是在长 Prompt 和 Chunked Prefill 场景下，可以避免大量无意义的 Vocabulary Projection。

## 10. V2 最终执行链

V2 当前完整 Serving 流程：

```text
Request
    ↓
Scheduler
    ↓
决定本轮 Request + Token 数
    ↓
KVCacheManager 分配 Physical Blocks
    ↓
ModelRunner
    ↓
构造 Packed Input
    ├── input_ids
    ├── positions
    ├── query_start_loc
    ├── seq_lens
    ├── block_table
    └── slot_mapping
    ↓
Transformer
    ↓
Attention
    ├── slot_mapping 写入当前 KV
    └── block_table + seq_lens 读取历史 KV
    ↓
hidden_states
    ↓
logits_indices
    ↓
Selective Logits Computation
    ↓
Sampling
    ↓
Append Output Token
    ↓
下一轮 Scheduling
```

---

## 11. V2 相比 V1 的核心变化

```text
V1
[B, T] + Padding
全量序列重复 Forward
无 KV Cache
职责混杂
所有 Hidden State 都计算 Logits
```

变为：

```text
V2
Packed [N]
Paged KV Cache
只计算尚未计算的 Token
Chunked Prefill
Mixed Prefill / Decode
重新划分 Scheduler / KVCacheManager / ModelRunner / Attention
Selective Logits Computation
```

V2 的核心不只是增加 KV Cache，而是把整个推理过程从：

> “对一批完整序列重复执行模型”

转变为：

> “Scheduler 每轮只选择真正需要继续计算的 Token，Packed 后执行，并利用 KV Cache 保存历史计算结果。”
